The 12 address-input development actions are the first twelve rows. Their `address` field accepts a private Bluetooth locator as free text; the action responses are designed to omit it. The five configured-entry actions are the remaining rows and require no MAC input. Serial/System ID probes read private identity bytes internally, but their responses suppress the bytes. The advertisement re-arm action changes Home Assistant's in-memory advertisement history; it is not a persistent write. The stable refresh changes the existing sensor state, which may be recorded by ordinary Home Assistant Recorder configuration; it does not backfill old measurement times. The history action returns a private list without changing that sensor.

The older address-input probes share a **global `probe_lock` with each other**, not the configured entry's `gatt_lock`. The refresh, history action, and P4 readiness probe use the per-entry GATT lock. This means the legacy probes are not coordinated with a simultaneous configured-entry transaction on the same meter. This is a concrete reason to retire their public registrations later; it is not evidence of an observed collision or security exploit. Multiple configured entries remain independently lockable for the product/P4 paths.

## Home Assistant guidance and product decision

[Home Assistant's current service-action guidance](https://developers.home-assistant.io/docs/dev_101_services/) describes registered integration actions in `services.yaml`, translations, field grouping, and response data. It recommends response data for results that do not fit an entity state; the bounded history list fits that purpose. The current documentation describes collapsing **fields** within an action, but no supported flag to hide a registered action from Developer Tools while keeping it callable was found. This is a bounded documentation finding, not a claim that no internal mechanism exists. [HA's action setup rule](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/action-setup/) recommends registration in `async_setup` and input validation in the handler. [Sensor guidance](https://developers.home-assistant.io/docs/core/entity/sensor/) treats sensor state as a present value and states that a measurement state class yields a line chart. The project's private historical test list remains a response, not extra sensors or Recorder backfill.

Project decision: **future model A — register only normal product actions**. After both physical gates and before the next public release, remove the obsolete development action registrations, metadata, and translations in one separately authorized cleanup gate; preserve useful lower-level probe helpers and synthetic tests where they still support diagnosis or regression. No generic “developer mode,” hidden-action flag, or new diagnostic action is proposed. The two product actions remain registered. P4 registration must remain until its naturally occurring post-measurement comparison closes; this audit makes no change to it. If a later physical gate requires a research action, authorize that explicitly rather than keeping the entire reverse-engineering surface indefinitely.

Seventeen choices under Developer Tools → Actions can obscure the two user features and invite accidental connection/record reads. The address-input probes demand a private locator that configured users should not need to handle. The chronology probe, current refresh, and history action return private health values/times; action responses can be copied into scripts, automation traces, screenshots, or issue reports by users. The history service description already warns against that. Structural probe results do not make the underlying GATT operation harmless to run concurrently or in an unintended meter state. These are UX and privacy exposure considerations, not a demonstrated vulnerability. No result or private identifier is included in this audit.
