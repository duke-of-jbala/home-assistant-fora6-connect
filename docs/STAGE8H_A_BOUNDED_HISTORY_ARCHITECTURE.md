## One historical measurement and bounded results

One eligible historical measurement is **one successfully read primary raw slot** in a single supported snapshot whose paired `0x25`/`0x26` responses validate, whose analyte is identified uric acid, whose category is General, whose value is not the invalid sentinel, and whose product mapping yields native mg/dL. The adjacent QC-invalid companion validates the known snapshot shape but is **not** a second user measurement. Do not infer a person's identity, a durable sample ID, or a stable place in a larger buffer from this definition.

| Conceptual field | Internal model | Private action response | Future normal UI |
| --- | --- | --- | --- |
| Raw slot index and snapshot count | Keep to explain this bounded read and diagnose unexpected shape. | Raw index is useful as a transient within-response reference; count can be reported. Neither is a persistent ID. | Omit by default. |
| Analyte, General category, validity | Required to accept each primary. | Successful list may state `uric_acid`/`mg/dL`; do not expose QC companion detail as a measurement. | Label as uric acid; omit internal codes. |
| Native mg/dL value | `Decimal` product value. | Private numeric value; JSON serialization policy must preserve supported precision. | Display only in an explicitly chosen private history surface. |
| Meter-local minute | Keep naive calendar fields, separate from any read/sync time. | A timezone-free `YYYY-MM-DD HH:MM` string **and explicit** `meter_local_time_timezone_known: false` or an equivalent labelled structure. Never append `Z` or offset. | Display as “meter-local time; timezone unknown”. |
| Pair/companion relation | Validate adjacent odd QC-invalid companion and its expected role. | At most a structural validation status if useful; no companion value/time. | Omit. |
| Store/source scope | One configured meter, one invocation, raw count 2 or 4. | Count and bounded result only; no MAC, serial, proxy, or raw frame. | Identify the already configured meter through the UI context, not a new history identity. |

For count **2**, require the complete `0,1` snapshot and return **one** eligible raw-0 General uric-acid measurement. Raw 1 is validated as the QC-invalid companion and is excluded. For count **4**, require the complete `0,1,2,3` snapshot and return **both** eligible raw-0 and raw-2 General uric-acid measurements. Raw 1/3 are excluded. The Stage 7H winner is still one reading for the current-state sensor; history is a list of the two valid observations.

## Chronology and timestamp policy

Order the returned list by parsed **meter-local minute, newest first**, never by raw index or the wire field labelled newest index. This is a relative wall-clock ordering of the returned snapshot only. Meter clock changes and unknown timezone prevent claims about absolute UTC time or chronology beyond the supplied meter-local fields. An equal-minute pair remains two valid historical measurements: return both, mark their relative order **ambiguous**, and use ascending raw index only as a documented stable presentation tie-breaker. The tie-breaker carries no temporal meaning. Stage 7H must continue to fail closed for its single-current-winner selection on that same tie.

Invalid calendar fields are parser failures; do not coerce them or substitute HA receive time. A missing timestamp, unreadable primary, or unreadable companion makes this v1 bounded snapshot fail as a whole. A success response must never silently omit a planned primary and claim a complete history list. Report count 2 or 4 only after validated metadata; fail closed for every other count. A repeated read can return the same records again, and a later read can change if the meter store changes. No stable fingerprint, deduplication, resume cursor, imported-history database, or historical state restoration is part of Stage 8H.

The private response should preserve **minute precision**, such as `YYYY-MM-DD HH:MM`, with an explicit timezone-unknown label/flag. A JSON string without offset is a wall-clock transcription, **not** an ISO instant suitable for conversion by HA, a browser, or an automation. The current project `MeterLocalTimestamp` and `Fora6Measurement` already keep timezone-naive time. Ingestion or action execution time, if ever reported, must have a separate name and its actual timezone; it must not replace the meter time.

## Home Assistant guidance and presentation decision

**Official HA behavior:** [integration service actions](https://developers.home-assistant.io/docs/dev_101_services/) may return a JSON-serializable dictionary and are specifically suitable for a response stream of objects that does not fit a single entity state. Current guidance says errors should be raised as action exceptions, rather than encoded as error codes that callers must inspect. The [config-entry action guidance](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/action-setup/) shows global registration and loaded-entry selection. A later Stage 8H-B action should use the appropriate response support mode for a required read result, target the existing entry, and return one or two objects only after a successful complete read and clean cleanup. Its exact public schema and error classes are an implementation decision; candidate names include `raw_slot_count`, `eligible_measurement_count`, `measurements`, `raw_index`, `uric_acid_value_mg_dl`, `meter_local_time`, and an explicit timezone-unknown/chronology-ambiguity field. Status can be operational; avoid exposing private exception messages.

**Official HA behavior:** [Recorder](https://www.home-assistant.io/integrations/recorder) stores entity state changes and can store events, with History, dashboard graphs, and statistics reading that database. An ordinary state written when the action runs represents an HA observation/update at that time; it does **not** relocate an old meter measurement to its original local minute. [Sensor guidance](https://developers.home-assistant.io/docs/core/entity/sensor/) says `SensorStateClass.MEASUREMENT` represents a present measurement and is an opt-in to long-term statistics; attributes can also enter Recorder unless excluded. The existing sensor has no such state class. This review found no supported ordinary entity API in that guidance that makes a timezone-unknown meter-local sample into a correctly backdated Recorder state. Stage 8H excludes Recorder and statistics backfill, so it must not manipulate Recorder internals or add synthetic historical entity updates. This is a project architecture inference from the documented HA state/Recorder model and the unknown meter timezone, not a claim that every possible third-party history design has been surveyed.

**Project semantics:** uric-acid tests are discrete observations. Connecting points with a continuous line implies values between tests that the meter did not measure. A later dedicated history view should favor a labelled **list/table and/or points-only scatter presentation**; a trend line may be a user-facing derived visualization only after a separate design decision. A HA History line for the current sensor reflects state update timing, not a reconstructed meter test series. A future richer view may consume explicitly supplied discrete records with meter-local labels while keeping the current sensor separate; no frontend or card is designed here.

| Candidate initial mechanism | Assessment |
| --- | --- |
| Manual response action | Fits an explicit bounded one/two-object read, no integration-owned persistence, no extra entity, and no claim that meter time is an HA state timestamp. **Chosen.** |
| Fire events or event entities | [HA event guidance](https://developers.home-assistant.io/docs/integration_events/) favors event entities for device events; these records are historical tests retrieved on demand, not newly occurring device events. The event bus/automations and possible Recorder storage increase health-data exposure. Rejected for initial Stage 8H. |
| Recent-record entities or attributes | Creates slot-based identity/churn or stale “previous” states; HA records publication-time state changes/attributes. Repeat reads could look like new tests and private values could persist. Rejected. |
| Backfill current sensor History or statistics | Unsupported for this scope and semantically wrong with unknown timezone; prohibited by Stage 8H. Rejected. |
| Custom history frontend | Could later show points and explicit meter-local labels, but needs separate data/privacy and UI design. Deferred. |

## Privacy, lifecycle, and failure contract for Stage 8H-B

An action response is the **least integration-persistent** candidate, not a guarantee that health data stays secret or ephemeral throughout HA. HA's [action documentation](https://www.home-assistant.io/docs/scripts/perform-actions) permits response variables in scripts and automations; a user who routes the response to notifications, templates, traces, or external systems can persist or redistribute it. Stage 8H-B should keep results only in the direct, explicitly invoked response and document that users should avoid automations and sharing action output. No health values/times in events, entity attributes, diagnostics, debug logs, exception text, or new Recorder/statistics writes. The existing current sensor's normal HA state and its Recorder policy remain unchanged.

Use the existing per-entry GATT exclusion so history cannot overlap current refresh or P4; never create automatic callbacks, polling, startup reads, or retries. A successful history action reads only and leaves current `MeasurementState`, `synchronized_at`, sensor availability, and entity count unchanged. Keep the existing normal manual-ON instruction; there is no evidence that post-measurement flashing works for this read, and P4 is investigating that state separately. Unload/cancellation must clean up the session. No copy/deployment is needed for this Stage 8H-A review.

The initial history read should be **all-or-nothing**: validate configured identity/project, notification subscription, metadata count, every fixed timestamp/value pair, primary semantics, companion shape, and cleanup before returning measurements. Reject unsupported count, missing/invalid metadata, malformed timestamp, invalid value or non-General/unknown primary, unexpected companion, and partial reads without a partial successful list. Preserve a primary failure when cleanup also fails, report cleanup separately through sanitized diagnostics where possible, and never return private measurements on incomplete cleanup. Equal-minute valid primaries are **not** a failure; mark ambiguity in their relative order. Follow current HA action guidance by surfacing operational failures as sanitized action exceptions rather than treating an `error_code` field as a successful response. Exact stage/code presentation, including dual failure/cleanup detail, needs Stage 8H-B design and tests.
