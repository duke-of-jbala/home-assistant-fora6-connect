The single-meter limitation is recorded in [Stage 6B3](STAGE6B3_FACTORY_MAC_IDENTITY.md).

**Later Stage 6B3 policy:** [the factory MAC migration](STAGE6B3_FACTORY_MAC_IDENTITY.md) supersedes the earlier placeholder-entry deferral after the user-run System ID result was unusable. Its in-place setup path awaits real HA validation; no actual identifier is published.

**Later physical regression:** the user installed Stage 6B1 and observed that the existing device and uric-acid entity remained, the false serial label disappeared, the Add card stayed suppressed, and Bluetooth connection metadata remained. ## Evidence and boundary

The user saw a second FORA 6 Connect discovery card for an already configured GD82. The local HA device page displayed the literal text “Serial Number” in the serial field. During this review, the user privately checked that the **ConfigEntry unique ID itself is exactly that literal text**. The user also privately confirmed that the displayed HA Bluetooth connection address matched the physical meter's printed BT MAC. Neither identifier nor the label photo is tracked. Equality between the printed serial and GATT `0x2A25` remains unconfirmed.

The intended identity architecture requires a *meter-specific* GATT `0x2A25` serial as ConfigEntry unique ID and `(DOMAIN, serial)` device identifier. This existing entry instead contains a generic literal label, so its device-specific identity is **not established**. The integration does not silently rewrite the existing entry or derive a replacement from its MAC, project, name, or opaque data. The Bluetooth address remains a mutable transport locator and `CONNECTION_BLUETOOTH` connection, never a logical ID. Project `0x4183` confirms the model path only. No meter IP is assigned.

## Cause and correction

The existing Bluetooth Config Flow accepted a matching advertisement and showed the confirmation form **before** checking whether `ConfigEntry.data["address"]` already held that locator. The duplicate serial check ran only after user confirmation and active identity reads. The flow now aborts `already_configured` immediately for a known address, and checks again when the confirmation form is submitted to cover an entry created while the form was open. This path performs no FORA exchange or extra serial read.

The sensor already passed `entry.unique_id` to `DeviceInfo.serial_number`; there was no display-label constant in that assignment. Config Flow assigns `unique_id` solely from its `0x2A25` read, and the user's private check found the stored unique ID is exactly “Serial Number”. Thus the display reflects the stored identity text; the evidence strongly indicates the GATT read supplied a generic placeholder during original setup, though the original raw read was deliberately not published. Earlier structural checks tested UTF-8/printability and repeat stability, which a placeholder can pass. The integration now rejects this literal for **new** setup flows. Existing entries are preserved, but the sensor and setup-time registry reconciliation clear `serial_number` from the visible device metadata rather than showing the placeholder as a physical serial. No BLE read is done to render metadata. A real meter-specific identity and migration need a separate evidence gate.

## New locator and conflicts

An unknown address still enters the guarded user confirmation flow. It must pass the existing `0x22`/`0x24` project `0x4183` confirmation and one read-only `0x2A25` acquisition. If that read yields the placeholder, setup fails without creating an entry or changing a locator. If it yields a usable non-placeholder exact serial matching an existing entry, the existing second review step can update the locator. The old locator must no longer be connectable and another entry must not claim the new locator. Only then does the registry replace its Bluetooth connection with the new locator, preserving non-Bluetooth connections, and the ConfigEntry address is updated. If the entry update fails, the registry's previous connections are restored where possible. The runtime locator changes only after successful entry update. No second entry, device, or entity is created. **The current placeholder-identified entry cannot use this same-serial relocation path safely.**

A new serial can create a separate entry only through the full confirmation path. If another entry claims the candidate address during active confirmation, the existing identity conflict check fails closed. A previously configured address is suppressed without an active read, so this path does not prove what serial a later advertiser at that address would report. It simply refuses a new flow or locator merge. Unreadable serial or failed project confirmation never changes the existing identity or locator; no MAC fallback exists.

Home Assistant's current [Config Flow API](https://github.com/home-assistant/core/blob/dev/homeassistant/config_entries.py) supports current-entry checks and serial-backed unique IDs. The current [device registry API](https://github.com/home-assistant/core/blob/dev/homeassistant/helpers/device_registry.py) supports entry-scoped identifier lookup and `async_update_device(..., new_connections=..., serial_number=...)`. The [registry guidance](https://developers.home-assistant.io/docs/device_registry_index/) states that entity `device_info` is read during config-entry entity registration. `new_connections` replaces rather than accumulates old Bluetooth locators.

## Existing installation and validation

Install the corrected integration and reload its ConfigEntry or restart Home Assistant. The setup reconciliation updates the same registry device by its retained identifier; removing/re-adding the device is not the normal path. Verify that the serial field is **empty rather than the false label**, that device/entity counts remain one, and that a subsequent meter OFF/ON advertisement does not offer another Add card. Do not treat the current entry as having proven meter-specific identity. The next gate is a separately authorized, bounded private identity review, potentially using the observed readable standard System ID `0x2A23` and private printed-label comparison, before any ConfigEntry/DeviceInfo identity migration. A new-address scenario should be tested only after that gate. No production history synchronization or entity update was added.
