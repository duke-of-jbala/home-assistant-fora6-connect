# Stage 8 — current-state refresh hardening review

Stage 8 reviewed the physically validated Stage 7H manual refresh offline with synthetic tests. It adds one narrow error-reporting correction: a cleanup failure no longer hides an earlier connection, subscription, identity, metadata, or record failure. Both the primary error and separate cleanup errors remain private-data-free. No command sequence, sensor selection rule, entity, trigger, or persistence behavior changes. Stage 8H and Stage 9 have not begun.

## Repeat refresh and failure retention

Repeated refresh of the same measurement writes to the same `MeasurementState` and the same registered entity. It does not create an entry, device, or entity and does not explicitly import historical observations. A normal Home Assistant state write may still be recorded by HA's ordinary recorder; that is distinct from integration-driven historical backfill. Durable record deduplication is unnecessary for one current-state replacement.

The coordinator replaces state only after identity, all bounded record reads, semantic selection, and clean unsubscribe/disconnect succeed. Synthetic checks cover a successful reading followed by connection, subscription, timeout, unsupported count, equal-minute ambiguity, and cleanup failures; previous value and separate ingestion time remain unchanged. First-ever failures keep the entity unavailable. The existing single-entry lock rejects overlap; separate entries have separate runtime states and locks. Cleanup-only failure is reported as the primary error when nothing earlier failed.

## Availability, reload, and presentation decisions

The selected measurement and ingestion time are **process memory only**. Entry reload and HA restart create a fresh runtime and leave the entity unavailable until another explicit successful refresh. Unload disables the entry's coordinator; the sensor's state listener is removed by the entity lifecycle. Synthetic tests verify fresh runtime on reload. This behavior is deliberate for the first current-state product: automatically restoring an old health value could make an unrefreshed, potentially stale reading look current. It also avoids new persistence of private measurement data. If restoration is later authorized, [Home Assistant's sensor guidance](https://developers.home-assistant.io/docs/core/entity/sensor/#restoring-sensor-states) recommends `RestoreSensor`, since `RestoreEntity` stores a potentially converted state rather than the sensor's native value. Stage 8 does not implement restoration.

The ordinary entity exposes its mg/dL native value and availability only. It does not add `measurement_time_local`, a timezone attribute, a raw index, a status entity, or a diagnostic entity. The explicit private action response already gives the selected meter-local minute and the success/error status; the product measurement keeps that naive minute separate from the aware process-local ingestion time. An attribute could be reconsidered after UX review, but the meter timezone is unknown and a state-only view currently has fewer ways to confuse measurement and ingestion time.

The integration keeps the evidence-backed `raw / 10` mg/dL value as the native sensor value. It does not claim automatic HA conversion to mmol/L: this sensor has no matching unit-converting device class or `state_class`. The retained app's `mg/dL × 59.48 ÷ 1000` and two-decimal `FLOOR` record-display formatting are presentation behavior, not the integration's measurement model. [Home Assistant's sensor documentation](https://developers.home-assistant.io/docs/core/entity/sensor/) distinguishes native values/units from optional sensor-class conversion and long-term-statistics opt-in.

## Action UX and errors

`fora6_connect.refresh_current_uric_acid` retains its configured-entry selector; no Bluetooth address is entered. The action description already instructs: turn the meter on normally, leave history arrows untouched, then run the action. Missing, wrong-domain, and unloaded entry targets are rejected before BLE work. The private result reports bounded stages/codes, cleanup errors, count/selection status, and on success only the selected value and meter-local time. It does not return the MAC, serial, System ID, raw integer/frame, or digest.

Current error distinctions include: `no_connectable_device`/`resolution_failed` (unavailable), `connection_failed` and related connection codes, `subscription_failed`, `identity_mismatch`, `unexpected_project_id`, `unsupported_history_count`, `invalid_response`/`unexpected_companion`, `no_valid_uric_acid_primary`, `ambiguous_meter_local_time`, and cleanup codes. The subscription failure result is enough to identify the stage; the documented user remedy is to power the meter off and on normally, avoid history arrows, and retry manually. No automatic retry or speculative meter-state detection is added. The cause of the observed post-measurement subscription failure remains unknown.

## Lifecycle, multiple entries, metadata, and privacy

Global action registration happens in integration `async_setup`, not once per entry. Entry setup creates one runtime/coordinator and forwards one sensor platform without a BLE read; unload removes the sensor platform before disabling manual refresh. The sensor unique ID derives from the stable entry ID, so reload does not create a new registry identity. Synthetic setup/unload/reload and two-entry coordinator checks found no state or lock cross-talk. They are not a full running-HA multi-device test; only one real GD82 has been validated.

Device metadata remains `FORA 6 Connect` / `ForaCare` / `GD82`, with the canonical factory Bluetooth MAC as the existing ConfigEntry/DeviceInfo identifier and Bluetooth connection. The serial field remains absent: this meter's `0x2A25` text is a generic placeholder and its `0x2A23` System ID is unusable. Proprietary printed-serial retrieval remains a separate future evidence task. No identity policy changes here.

There is no implemented diagnostics payload. The refresh path does not log measurement values, meter-local times, identifiers, or frames. The private action response and normal HA entity state are the only intended health-data output; public tests use synthetic data. Stage 8 adds no historical store, dedup cursor, recorder backfill, polling, startup, advertisement, or post-measurement trigger.

## Readiness decisions

**Stage 8H:** Architecturally suitable for a separately authorized, configured-entry **manual action returning a bounded record list**. It should reuse the existing transport, per-entry single-flight policy, count-two/four gates, pair parser and semantic filtering, and expose validated uric-acid values with explicitly meter-local minute timestamps only in a private action response. It should not use an event, diagnostics payload, entity attributes, or recorder/statistics import. Its exact response/privacy policy and interaction with simultaneous current refresh need review in that stage; nothing is implemented here.

**Stage 9:** The code is ready for a separately authorized proxy-path validation plan without a prerequisite command or parser change. The current transport calls Home Assistant's [`async_ble_device_from_address(..., connectable=True)`](https://developers.home-assistant.io/docs/core/bluetooth/api/), which can resolve a configured local adapter or remote scanner. A successful FORA action alone does **not** prove which path carried it. Stage 9 must observe a current connectable advertisement, the selected connection route, a successful bounded manual refresh, and cleanup while associating the session with the intended ESPHome proxy. [Home Assistant's Bluetooth network map and adapter view](https://www.home-assistant.io/integrations/bluetooth/#viewing-your-bluetooth-adapters-and-proxies) can show scanner relationships; private HA/ESPHome connection diagnostics can corroborate the actual connection route. Any shared evidence must redact addresses, health values, and timestamps. Scanner objects, if inspected, are read-only and not retained. Physical validation has not occurred in Stage 8.

**Exact next proposed gate:** separately authorize Stage 9 explicit ESPHome Bluetooth Proxy path validation. Stage 8H bounded manual uric-acid history exposure is architecturally possible but optional and separately gated; it is not a prerequisite for Stage 9. Neither begins automatically. General history traversal, count six or more, dedup/resume, automatic refresh, and broad identity claims remain unproven.
