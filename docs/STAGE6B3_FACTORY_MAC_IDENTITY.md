# Stage 6B3 — factory Bluetooth MAC identity and in-place migration

## User-run Home Assistant migration result

After installing this build and restarting Home Assistant, the user observed that the existing integration entry remained; exactly one FORA device and one uric-acid entity remained; the entity was still Unavailable; and its device association was preserved. The bogus serial field was absent, Bluetooth connection metadata remained, the device still appeared as GD82 by ForaCare, and no discovery Add card appeared. A privacy-safe inspection of the ConfigEntry storage showed `ConfigEntry.unique_id` now has canonical six-octet lowercase colon-separated MAC form instead of the generic placeholder. The actual MAC was not included in the inspection output or repository.

This confirms successful in-place migration for the configured GD82: one entry, one device, one entity, no duplicate, and retained connection metadata. **Stage 6B3 is complete for its authorized migration scope.** It does not show that every GD82 has a fixed globally unique address. Address behavior after reset or firmware update, population-wide uniqueness, proprietary printed/app serial relationship, manufacturer-data semantics, and the exact HA scanner/proxy path remain unresolved. No further identity migration is required for this tested meter before continuing project work.

## Evidence and decision

The real GD82's GATT `0x2A25` text is the generic placeholder “Serial Number”, so repeat stability did not make it meter-specific. In the user-run Stage 6B2 read, standard System ID `0x2A23` was present, readable, and eight bytes, but the probe classified its value unusable. `set_reference` refused it and `compare` correctly reported `no_reference`. The private value is not published. The meter's factory label has both a serial and a BT MAC. The user privately matched the printed BT MAC to Home Assistant's observed Bluetooth address, and the observed address stayed the same across several meter OFF/ON cycles. This is evidence for **this meter under tested conditions**, not a population-wide or firmware-reset guarantee.

[Home Assistant Config Flow guidance](https://developers.home-assistant.io/docs/core/integration/config_flow/#unique-id-requirements) accepts a device MAC from discovery as a unique ID and recommends the device registry's `format_mac` convention. [Device registry guidance](https://developers.home-assistant.io/docs/device_registry_index/) documents entry-scoped identifiers/connections and matching an existing device by either. The [August 2026 registry guidance](https://developers.home-assistant.io/blog/2026/08/24/device-registry-follow-up-changes/) supports replacing full identifier/connection sets through `new_identifiers` and `new_connections`. Config-entry attributes must be changed through [`async_update_entry`](https://developers.home-assistant.io/blog/2024/02/12/async_update_entry/). These APIs support an in-place migration without removing the device or its entity.

For a project-confirmed GD82 with this exact generic `0x2A25` placeholder, the factory BLE MAC is accepted as the best available fallback identity. A genuinely meter-specific standard identity remains preferable if later established. The project ID, local name, placeholder text, and opaque manufacturer data are never unique IDs. The Bluetooth address is validated as exactly six colon-separated hexadecimal octets; canonical identity and registry connection use lowercase colon form, consistent with HA `format_mac`. The original HA locator text stays in `ConfigEntry.data["address"]` for transport resolution. No raw MAC is put into logs, action results, diagnostics, or public fixtures.

This decision distinguishes a factory-printed, repeatedly observed BT MAC on one GD82 from a general claim that all BLE addresses are fixed. Privacy addressing, replacement hardware, reset/update behavior, and collision frequency across GD82 production remain unresolved. A different MAC is treated as a different meter unless a later separately authorized identity mechanism proves otherwise. There is no silent locator merge using placeholder DIS fields.

## Setup and registry migration

The existing entry has the literal placeholder as `unique_id`. On setup/reload, before forwarding the sensor, migration requires a valid stored MAC, no other FORA entry already using that canonical ID, the existing device under the placeholder identifier, a single matching Bluetooth connection on that same device, and exactly one registered uric-acid entity already attached to it. Any mismatch fails closed without creating a replacement device or entity. It does not connect to the meter.

The same Home Assistant device ID receives `new_identifiers={(DOMAIN, canonical_mac)}`, a canonical `CONNECTION_BLUETOOTH` value, and `serial_number=None`. The same ConfigEntry object receives `unique_id=canonical_mac` through `hass.config_entries.async_update_entry`. Other device metadata, area and user customizations remain on the existing registry object. The uric-acid entity's unique ID is based on the unchanged ConfigEntry `entry_id`, so its entity registry entry and entity ID remain stable. If the entry update fails, the registry identifiers/connections/serial are restored. A rollback failure is reported by a privacy-safe setup error for manual review; no device is deleted. No user removal/re-add is expected.

For a new candidate, passive advertisement still only starts a review form. Active `0x22`/`0x24` project confirmation and the existing read-only `0x2A25` check must succeed first. When that read yields the known generic placeholder, the validated candidate MAC is the fallback `ConfigEntry.unique_id` and DeviceInfo identifier. A non-placeholder serial follows the earlier serial path. The confirmed factory MAC is shown only as Bluetooth connection metadata, never as `DeviceInfo.serial_number`; the printed proprietary serial is not entered or inferred.

Known configured MACs are suppressed before any active command, including case differences. Unknown MACs can enter the guarded confirmation flow. Two candidates with the same canonical MAC cannot create distinct entries. A different MAC is not merged with a MAC-identified entry. The current serial-based locator-update path remains only for genuinely non-placeholder serial identity; no migration of the placeholder entry to a new locator is inferred. No System ID read is added to Config Flow, because this meter's result is unusable and broader GD82 provisioning is unknown.

Actual printed serial, actual BT MAC, and System ID bytes remain outside Git and the task report.
