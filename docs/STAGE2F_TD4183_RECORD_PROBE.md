## Source and model path

The retained, private Stage 2B static artifacts outside Git are decompilations of the previously documented mirror-distributed iFORA HM 1.7.6 APK and 1.7.9 XAPK. Their package hashes, signing-certificate evidence, and authenticity limits are in [the Stage 2B register](STAGE2_IFORA_HM_STATIC_ANALYSIS.md). The 1.7.6 research runtime was patched and re-signed; the [sanitized Stage 2C capture](STAGE2C_GD82_LIVE_PROTOCOL_CAPTURE.md) confirms the real GD82's custom import path and the `0x25`/`0x26` participation, but does **not** publish their private record frames. The [real Stage 2E result](STAGE2E_HA_PROTOCOL_IDENTITY_PROBE.md) independently confirms Home Assistant's `0x22`/`0x24` identity exchange **with the meter ON**.

In the 1.7.9 decompilation, the project-code factory `g2/a.java` selects `d2/w.java` for `TD4183`; `d2/w.java` inherits `d2/C0428c.java`, which inherits `d2/AbstractC0426a.java`. The corresponding 1.7.6 classes are `z3/u.java`, `z3/c.java`, `z3/a.java`, and command builder `b4/a.java`. The physical Stage 2C/2E `0x4183` response connects this branch to the real GD82. Obfuscated identifiers and a JADX fallback for the large import thread limit certainty about the full app workflow.

## Selector and index reconciliation

Both retained enum definitions assign `CurrentUser = 0` and `User1 = 1`. Neither `0x2B` nor `0x25`/`0x26` builder applies `+1` to the enum value. The 1.7.6 import service selects `values()[import_extension + 1]`; for the observed `0x4183` project path, the extension defaults to zero, selecting `User1`. The retained 1.7.9 fallback import path likewise indexes the enum with an incremented extension. Thus the live `1` is **User1**, not a wire remapping of `CurrentUser`. The old all-zero constructors in commit `4ae3efa7a1993140afbfe4575b35917a11192dfd` selected `CurrentUser` and did not match the successful import's requests. This was discovered before any Home Assistant Stage 2F physical test.

This establishes the selector used by the successful app import on this physical GD82. It does not establish that every GD82 profile or future import should select User1.

Both builders place the raw record index low byte at byte 2 and high byte at byte 3, with no index `+1` conversion. The live index-one requests differ from index zero only at byte 2 and checksum. In both static versions the TD4183 handler's count method probes `raw_count - 1` to classify single versus multi-parameter storage before its higher-level import loop starts at logical index zero. A leading index-one pair is therefore consistent with a last-slot probe if the raw count was two; the private count response is not published here. The final index-one pair could be a companion slot in multi-parameter mode or a later logical slot, depending on the private response class. **The exact branch explaining the final index-one access remains unresolved.** The handler's low-level raw-slot method itself directly pairs `0x25` and `0x26` for a selected index without a prior index-one guard. This supports an independent index-zero request at the software call-path level, while physical acceptance without the app's other steps remains unproven.

The sanitized index-one wire requests were `51 25 01 00 00 01 A3 1B` and `51 26 01 00 00 01 A3 1C`. The observed pair ordering was index one, index zero, then index one. These request frames contain no health value or private device identifier; response payloads remain private.

Stage 2F selects **only User1 raw index zero** and does not loop, search adjacent indexes, or infer the analyte from the user's known measurement history. The `0x25`/`0x26` pair is the only paired raw-record method traced for this handler; that does not establish a universal rule for every meter state.

These three new requests are **read-oriented in the inspected TD4183 app path**: `0x2B` obtains count/slot metadata and `0x25`/`0x26` return a selected stored slot. Their constructors contain a selector and index, not a value to set. No meter-internal side effect can be ruled out from static code alone; Stage 2F therefore bounds them to one request each and excludes commands of uncertain purpose. The app's clock-set call is unconditional in the decompiled import thread, but no static record method checks a clock-set result as a prerequisite. Whether the physical meter accepts a record read without that call is **unresolved**. If it does not, this prototype must fail closed; it must not send `0x33` or add a fallback.

## Development-only transport boundary

The corrected `fora6_connect.probe_protocol_record` action takes a private runtime address, uses the same Home Assistant connectable resolver, subscription, one-response-at-a-time exchange, timeouts, and cleanup as Stage 2E, and requires valid wake/project/`0x4183` identity **before** the three new requests. It sends at most one User1 `0x2B`, one User1 `0x25` at index zero, and one User1 `0x26` at index zero, each with explicit `response=True` and no application retry. `0x33`, `0x27`, `0x28`, `0x2F`, and `0x50` are unreachable. The source evidence supports an eight-byte response envelope and matching command ID, not a public health-record fixture.

The action returns only semantic flags. A complete pair proves two matching response frames arrived; it does **not** prove analyte identity, decoded measurement, meter-local timestamp, or successful record import. Thus `analyte_identified`, `measurement_field_decoded`, and `uric_acid_scaling_applied` remain false. Raw notification bytes live in memory only until validation. The existing known uric-acid result is the controlled physical target, but the probe must not label the returned pair as uric acid without field evidence. No automatic sync, persistence, config flow, polling, or entities are introduced.
