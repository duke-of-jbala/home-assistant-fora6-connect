# Stage 2F — TD4183 single-record evidence and development probe

**State:** Offline evidence gate reviewed 2026-09-27; a bounded development-only Home Assistant implementation is permitted for the three read-oriented requests below. No physical Stage 2F result exists yet. Stage 2E identity validation remains a prerequisite. This document paraphrases static findings without redistributing application code or a private capture.

## Source and model path

The retained, private Stage 2B static artifacts outside Git are decompilations of the previously documented mirror-distributed iFORA HM 1.7.6 APK and 1.7.9 XAPK. Their package hashes, signing-certificate evidence, and authenticity limits are in [the Stage 2B register](STAGE2_IFORA_HM_STATIC_ANALYSIS.md). The 1.7.6 research runtime was patched and re-signed; the [sanitized Stage 2C capture](STAGE2C_GD82_LIVE_PROTOCOL_CAPTURE.md) confirms the real GD82's custom import path and the `0x25`/`0x26` participation, but does **not** publish their private record frames. The [real Stage 2E result](STAGE2E_HA_PROTOCOL_IDENTITY_PROBE.md) independently confirms Home Assistant's `0x22`/`0x24` identity exchange **with the meter ON**.

In the 1.7.9 decompilation, the project-code factory `g2/a.java` selects `d2/w.java` for `TD4183`; `d2/w.java` inherits `d2/C0428c.java`, which inherits `d2/AbstractC0426a.java`. The corresponding 1.7.6 classes are `z3/u.java`, `z3/c.java`, `z3/a.java`, and command builder `b4/a.java`. The physical Stage 2C/2E `0x4183` response connects this branch to the real GD82. Obfuscated identifiers and a JADX fallback for the large import thread limit certainty about the full app workflow.

The static app import thread starts its indexed loop at raw index `0`; the TD4183 handler can double an index for its multi-parameter mode. Raw index `0` is unchanged in either mode. Stage 2F selects **only raw index zero** and does not loop, search adjacent indexes, or infer the analyte from the user's known measurement history. The `0x25`/`0x26` pair is the only paired record method traced for this handler; that does not establish a universal rule for every meter state.

These three new requests are **read-oriented in the inspected TD4183 app path**: `0x2B` obtains count/slot metadata and `0x25`/`0x26` return a selected stored slot. Their constructors contain a selector and index, not a value to set. No meter-internal side effect can be ruled out from static code alone; Stage 2F therefore bounds them to one request each and excludes commands of uncertain purpose. The app's clock-set call is unconditional in the decompiled import thread, but no static record method checks a clock-set result as a prerequisite. Whether the physical meter accepts a record read without that call is **unresolved**. If it does not, this prototype must fail closed; it must not send `0x33` or add a fallback.

## Development-only transport boundary

The implemented `fora6_connect.probe_protocol_record` action takes a private runtime address, uses the same Home Assistant connectable resolver, subscription, one-response-at-a-time exchange, timeouts, and cleanup as Stage 2E, and requires valid wake/project/`0x4183` identity **before** the three new requests. It sends at most one `0x2B`, one `0x25` at index zero, and one `0x26` at index zero, each with explicit `response=True` and no application retry. `0x33`, `0x27`, `0x28`, `0x2F`, and `0x50` are unreachable. The source evidence supports an eight-byte response envelope and matching command ID, not a public health-record fixture.

The action returns only semantic flags. A complete pair proves two matching response frames arrived; it does **not** prove analyte identity, decoded measurement, meter-local timestamp, or successful record import. Thus `analyte_identified`, `measurement_field_decoded`, and `uric_acid_scaling_applied` remain false. Raw notification bytes live in memory only until validation. The existing known uric-acid result is the controlled physical target, but the probe must not label the returned pair as uric acid without field evidence. No automatic sync, persistence, config flow, polling, or entities are introduced.

**Next gate after implementation:** one user-run physical Home Assistant action on the existing stored record, with a privacy-safe result only. Stage 2F stays in progress until that result is reviewed. If the meter requires a clock-setting prerequisite or yields an unexpected response, stop without another command and revisit the evidence gate.
